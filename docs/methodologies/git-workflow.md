# Методология: git-процесс

Справочник по ветвлению, коммитам и релизам. Жёсткие запреты (не коммитить без просьбы,
не переписывать историю) — в конституции, §5.

## Модели ветвления

| Модель | Когда подходит | Чем платим |
| --- | --- | --- |
| Trunk-based (короткие ветки от `main`) | Частые релизы, есть CI и тесты | Нужны фича-флаги для незавершённого |
| GitHub Flow (ветка → PR → `main`) | Дефолт для продуктовой команды | Требует дисциплины по размеру PR |
| Git Flow (`develop`, `release/*`, `hotfix/*`) | Версионируемые релизы, длинная стабилизация | Много ветвлений и слияний, медленно |
| Release branches | Поддержка нескольких версий одновременно | Дорогой бэкпорт исправлений |

Дефолт: короткие ветки от `main` и небольшой PR. Ветка живёт часы или дни, не недели —
чем дольше, тем дороже конфликты.

## Имена ветвей

`<тип>/<краткое-описание>`: `feat/order-export`, `fix/login-timeout`,
`refactor/api-client`, `chore/deps-bump`. Номер задачи в начале, если так принято в
проекте: `feat/PROJ-142-order-export`.

## Коммиты

Conventional Commits: `тип(область): краткое описание` в повелительном наклонении, до ~72
символов, без точки в конце.

Типы: `feat`, `fix`, `refactor`, `perf`, `docs`, `style`, `test`, `build`, `ci`, `chore`.
Ломающее изменение — `!` после области и секция `BREAKING CHANGE:` в теле.

В теле — **зачем**, а не пересказ diff: какую проблему решаем, почему выбран такой путь,
что осознанно не сделали. Один коммит — одно логическое изменение; форматирование и
переименования отдельными коммитами, чтобы ревью читалось.

## Pull request

- Размер: цель — до ~400 изменённых строк без учёта сгенерированного. Больше — делим.
- Описание: что и зачем, как проверить, что осталось за рамками, скриншоты для UI.
- Самопроверка до запроса ревью: локально проходят линтер, типы, тесты, сборка.
- Ревью смотрит корректность, границы, тесты и читаемость. Стиль — работа линтера, не
  человека.
- Замечания закрываются либо правкой, либо аргументом; молча проигнорированных нитей не
  остаётся.

## Слияние

| Способ | Когда |
| --- | --- |
| Squash | Дефолт: ветка с шумной историей превращается в один осмысленный коммит |
| Merge commit | Когда важна история ветки (крупная фича с логичными шагами) |
| Rebase and merge | Линейная история, каждый коммит осмыслен и проходит тесты |

Перед слиянием ветка подтягивает актуальный `main`. Конфликты решает автор ветки — он
знает контекст.

## Релизы

Семантическое версионирование: `major` — ломающее, `minor` — новая функциональность,
`patch` — исправления. Тег на коммите релиза, changelog собирается из conventional
commits. Хотфикс идёт от тега релиза и потом переносится в `main`.

## Гигиена

`.gitignore` закрывает артефакты сборки, зависимости, локальные конфиги и `.env`. Секрет,
попавший в историю, считается утёкшим: сначала отзыв и ротация, потом чистка истории.
Большие бинарники — в LFS или во внешнее хранилище, не в репозиторий.
